# LLM Wiki v2

- 来源：https://gist.github.com/rohitg00/2067ab416f7bbe447c1977edaaa681e2
- https://mp.weixin.qq.com/s/D1-sKka_lm58FTi_F8xuow?poc_token=HFLP-2mjgOmd9Vxc-MoYUhJHjQAQScf05nnIRLIh

> V1 火了之后，大量开发者开始实战。很快，一个真实的问题浮出水面——知识库越大，噪音越多。
> 开发者 Rohit Ghumare 跑了一段时间 V1 之后，发现了一个挺尴尬的事：
> 当 Wiki 超过 200 页，全靠一个索引文件导航就开始力不从心了。更头疼的是，所有知识都被等权对待——三个月前的一条临时笔记和一篇核心论文的摘要在系统眼里"地位"一样。
> 他推出的 LLM Wiki V2，就是来解决这些"规模化之后的问题"。
> 升级一：每条知识都有了"保质期"
> 升级二：模仿人脑的四层记忆，工作记忆、情节记忆、语义记忆、程序记忆
> 升级三：知识之间有了"关系标签"
> 升级四：三种搜索一起上，BM25 关键词搜索、向量语义搜索、图谱遍历
> 升级五：AI 自己管理知识库

一种使用 LLM 构建个人知识库的模式。基于构建 [agentmemory](https://github.com/rohitg00/agentmemory)（一个面向 AI 编程 Agent 的持久记忆引擎）的经验进行了扩展。

本文档建立在 [Andrej Karpathy 的原始 LLM Wiki 创意文档](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)之上。原始文档中的一切仍然适用。本文档补充了我们在生产环境中运行该模式所学到的东西：规模化后会出什么问题、缺了什么，以及什么区分了一个持续有用的 wiki 和一个腐烂的 wiki。

## 原版做对了什么

核心洞察是正确的：**停止重新推导，开始编译。** RAG 检索后即遗忘。wiki 积累并复利增长。三层架构（原始来源、wiki、schema）是有效的。操作（摄入、查询、检查）覆盖了基本需求。如果你还没读过原版，从那里开始。

以下是我们构建和运行该模式数千个会话后发现的问题。

## 缺失的一层：记忆生命周期

原版将所有 wiki 内容视为永远同等有效。实际上，知识有生命周期。你上周发现的 bug 比六个月前的更重要。你见过十二次的模式比只见过一次的更可靠。来自较新来源的论断应该自动削弱较旧的论断。

**置信度评分。** wiki 中的每个事实都应携带置信度分数：有多少来源支持它、最近何时被确认、是否有矛盾。当 LLM 写下"项目 X 使用 Redis 做缓存"时，该论断应知道自己来自两个来源、三周前最后确认、置信度为 0.85。置信度随时间衰减，随强化而增强。这将 wiki 从等权论断的平铺集合转变为活模型，LLM 可以说"我对 X 相当确定但对 Y 不太确定"。

**取代。** 当新信息与现有论断矛盾或更新时，旧论断不应只是带着标注留在那里。新论断应明确取代旧论断。链接、加时间戳、旧版本保留但标记为过时。知识的版本控制，不仅仅是文件的版本控制。

**遗忘。** 不是一切都应该永远保留。一个从不遗忘的 wiki 会变得嘈杂。实现一条保留曲线：曾经重要但数月未被访问或强化的事实应逐渐淡出。不是删除，而是降低优先级。LLM 的等效操作是把东西移到最底层抽屉。艾宾浩斯遗忘曲线在这里效果很好：保留率随时间指数衰减，但每次强化（访问、新来源确认）会重置曲线。架构决策衰减缓慢。临时 bug 衰减快速。

**巩固层级。** 原始观察与已确立的事实不同。构建一个管道：
- **工作记忆**：近期观察，尚未处理
- **情节记忆**：会话摘要，由原始观察压缩而来
- **语义记忆**：跨会话事实，由情节整合而来
- **程序记忆**：工作流和模式，从反复出现的语义中提取

每一层比下一层更压缩、更可信、更持久。LLM 随着证据积累将信息逐层提升。这就是你从"我见过一次"到"事情就是这样运作的"的路径。

## 超越扁平页面：知识图谱

原版 wiki 是带 wikilink 的页面。这能工作，但你白白浪费了结构信息。你真正想要的是在页面之上叠加一个有类型的知识图谱。

**实体提取。** 当 LLM 摄入来源时，不应只写散文。它应提取结构化实体。人物、项目、库、概念、文件、决策。每个实体获得类型、属性和与其他实体的关系。"React" 是一个库。"认证迁移" 是一个项目。"Sarah" 是一个人，她负责认证迁移并对 React 有自己的看法。

**类型化关系。** 并非所有连接都等同。"使用"、"依赖"、"矛盾"、"导致"、"修复"、"取代" 承载不同的语义权重。一个说"A 与 B 相关"的链接不如"A 导致了 B，由 3 个来源确认，置信度 0.9" 有用。

**查询的图遍历。** 当有人问"升级 Redis 的影响是什么？"时，LLM 不应只做关键词搜索。它应从 Redis 节点出发，沿"依赖"和"使用"边向外遍历，找到所有下游内容。这能捕捉关键词搜索遗漏的连接。

图谱不取代 wiki 页面。它增强页面。页面用于阅读。图谱用于导航和发现。

## 真正可扩展的搜索

原版依赖 `index.md`——一个编目所有页面的单一文件。这在约 100-200 页内有效。超过这个范围，索引本身变得太长，LLM 无法一次读完，你需要真正的搜索。

**混合搜索。** 最佳方案结合三个流：
- **BM25**（带词干提取和同义词扩展的关键词匹配）
- **向量搜索**（通过嵌入的语义相似度）
- **图遍历**（实体感知的关系遍历）

使用倒数排名融合合并结果。每个流捕捉其他流遗漏的内容。BM25 找到精确术语。向量找到语义相似性。图谱找到结构连接。三者结合胜过任何单一方法。

保留 `index.md` 作为人类可读的目录，但超过约 100 页后不要依赖它作为 LLM 的主要搜索机制。

## 自动化：从手动到事件驱动

原版最大的实践缺口是一切都是手动的。你放入来源并告诉 LLM 处理。你记得定期运行检查。你决定何时将答案归档。

实际上，你需要钩子。自动触发的事件：

- **新来源时**：自动摄入、提取实体、更新图谱、更新索引
- **会话开始时**：根据近期活动从 wiki 加载相关上下文
- **会话结束时**：将会话压缩为观察、归档洞察
- **查询时**：检查答案是否值得归档（质量分数 > 阈值）
- **记忆写入时**：检查与现有知识的矛盾，触发取代
- **定时调度**：定期检查、巩固、保留衰减

策展和方向仍应有人工介入。但簿记——让人们放弃 wiki 的那部分——应该完全自动化。

## 质量与自纠错

并非所有 LLM 生成的内容都是好的。没有质量控制，wiki 会积累噪音。

**给一切打分。** LLM 写的每条内容都应有质量分数。结构是否良好？是否引用来源？是否与 wiki 其余部分一致？可以让 LLM 自评，或用不同提示做第二轮评估。低于阈值的内容标记为待审查或重写。

**自我修复。** 原版的检查操作不应只是建议。它应自动修复能修复的。孤立页面被链接或标记。过时论断被标记。断裂的交叉引用被修复。wiki 应自行趋向健康，而不仅仅在你记得询问时。

**矛盾解决。** 原版提到了标记矛盾。那是第一步。第二步是解决矛盾。LLM 应根据来源时效性、来源权威性和支持观察数量来提出哪个论断更可能正确。人可以覆盖，但默认行为通常应该是正确的。

## 多 Agent 与协作

原版是单用户、单 Agent。许多真实用例涉及多个 Agent 或多人贡献同一个知识库。

**网格同步。** 如果多个 Agent 并行工作（不同编码会话、不同研究线程），它们的观察需要合并到共享 wiki。最后写入胜出在大多数情况下有效。对于冲突，使用基于时间戳的解决并支持人工覆盖。

**共享与私有。** 一些知识是个人的（我的偏好、我的工作流）。一些是共享的（项目架构、团队决策）。wiki 需要作用域。私有观察在提升时汇入共享知识。

**工作协调。** 当多个 Agent 在同一知识库上工作时，它们需要轻量协调。谁在做什么。什么被阻塞。什么已完成。不是完整的任务管理系统，只是足够防止重复工作和跟踪进度。

## 隐私与治理

原版没提这个，但它很重要。来源通常包含敏感信息：API 密钥、凭证、私人对话、个人身份信息。

**摄入时过滤。** 在任何内容进入 wiki 之前，剥离敏感数据。API 密钥、令牌、密码、标记为私有的内容。这应该是自动的，不是你记得要做的事。

**审计追踪。** wiki 上的每个操作（摄入、编辑、删除、查询）都应记录时间戳、变更内容和原因。这是你的问责层。当 wiki 中有什么看起来不对时，审计追踪告诉你它是怎么来的。

**带治理的批量操作。** 随着 wiki 增长，你会想批量删除过时内容、导出子集或合并重复实体。这些操作应被审计且可逆。

## 结晶化：从探索中复利

原版提到"好的答案可以作为新页面归档回 wiki"。这可以走得更远。

**结晶化**是将一个已完成的工作链（一个研究线程、一个调试会话、一次分析）自动蒸馏为结构化摘要的过程。问题是什么？我们发现了什么？涉及哪些文件/实体？得出了什么教训？这个摘要成为一等 wiki 页面，教训被提取为独立事实来强化知识库。

你的探索也是一种来源，就像一篇文章或一篇论文。wiki 应该这样对待它们。摄入结果、更新图谱、强化或质疑现有论断。

## 超越 Markdown 的输出格式

原版提到了 Marp 做幻灯片和 matplotlib 做图表。wiki 的输出不应局限于 Markdown 页面。根据查询，正确的输出可能是：

- 对比表格
- 时间线可视化
- 依赖关系图
- 用于展示发现的幻灯片
- 用于进一步分析的结构化数据导出（JSON、CSV）
- 给团队中其他人的简报

wiki 是知识存储。输出格式取决于受众和问题。

## Schema 才是真正的产品

原版暗示了这一点，但值得直说：**schema 文档（CLAUDE.md、AGENTS.md）是系统中最重要的文件。** 它将通用 LLM 转变为有纪律的知识工作者。它编码了：

- 你的领域中存在哪些类型的实体和关系
- 如何摄入不同种类的来源
- 何时创建新页面 vs 更新现有页面
- 应应用什么质量标准
- 如何处理矛盾
- 巩固计划是什么样的
- 什么是私有的 vs 共享的

你和 LLM 随时间共同演进这个文档。第一版会很粗糙。经过几十个来源和几次检查后，你会拥有一个反映领域实际运作方式的 schema。这个 schema 是可迁移的。分享给在类似领域工作的人，他们就能快速起步。

## 实现路径

这一切都是模块化的。你不需要第一天就拥有所有东西。

**最小可行 wiki**：原始来源 + wiki 页面 + index.md + 描述摄入/查询/检查工作流的 schema。这大致就是原版描述的。它有效。从这里开始。

**添加生命周期**：置信度评分、取代、基本保留衰减。这防止 wiki 变成杂物抽屉。

**添加结构**：实体提取、类型化关系、知识图谱。这让查询更好，暴露扁平页面会遗漏的连接。

**添加自动化**：自动摄入、自动检查、上下文注入的钩子。这是维护负担降到接近零的地方。

**添加规模**：混合搜索、巩固层级、质量评分。这是 wiki 增长到数百页后需要的。

**添加协作**：网格同步、共享/私有作用域、工作协调。这是面向团队或多 Agent 设置的。

根据你的需求选择入口。该模式在每个层级都有效。

## 为什么这很重要

Karpathy 的原始洞察仍然成立：瓶颈是簿记，而 LLM 消除了这个瓶颈。我们添加的是让 wiki 在规模化时保持健康的机制。生命周期管理防止知识腐烂。结构防止连接丢失。自动化让人专注于思考而非归档。质量控制让 wiki 随时间赢得信任。

Memex 终于可以建造了。不是因为我们有更好的文档或更好的搜索，而是因为我们有了真正能做这些工作的图书管理员。
