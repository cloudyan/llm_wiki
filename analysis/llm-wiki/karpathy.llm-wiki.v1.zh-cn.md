# LLM Wiki

- 来源：https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f

一种使用 LLM 构建个人知识库的模式。

这是一份理念文档，设计目的是让你复制粘贴到自己的 LLM Agent（例如 OpenAI Codex、Claude Code、OpenCode / Pi 等）中。它的目标是传达高层思想，而你的 Agent 会与你协作来构建具体实现。

## 核心思想

大多数人对 LLM 和文档的体验类似于 RAG：你上传一批文件，LLM 在查询时检索相关片段，然后生成答案。这能工作，但 LLM 每次都在从零重新发现知识。没有积累。问一个需要综合五份文档的微妙问题，LLM 每次都得找到并拼凑相关片段。没有任何东西被沉淀下来。NotebookLM、ChatGPT 文件上传以及大多数 RAG 系统都是这种模式。

这里的思路不同。与其在查询时仅从原始文档检索，LLM **增量地构建和维护一个持久的 wiki**——一个结构化的、互相链接的 Markdown 文件集合，位于你和原始来源之间。当你添加一个新来源时，LLM 不只是为后续检索做索引。它会阅读来源、提取关键信息，并将其整合到现有 wiki 中——更新实体页面、修订主题摘要、标注新数据与旧论断的矛盾之处、强化或质疑不断演化的综合结论。知识被编译一次，然后*持续保持最新*，而非在每次查询时重新推导。

这是关键区别：**wiki 是一个持久的、复利增长的产物。** 交叉引用已经存在。矛盾已经被标记。综合结论已经反映了你读过的所有内容。每添加一个来源、每提一个问题，wiki 都会变得更丰富。

你从不（或很少）亲自编写 wiki——LLM 负责编写和维护全部内容。你负责寻找来源、探索方向和提出正确的问题。LLM 承担所有繁杂工作——总结、交叉引用、归档和簿记，这些才是让知识库随时间真正有用的关键。在实践中，我一边开着 LLM Agent，另一边开着 Obsidian。LLM 根据我们的对话进行编辑，我实时浏览结果——追踪链接、查看图谱视图、阅读更新的页面。Obsidian 是 IDE；LLM 是程序员；wiki 是代码库。

这适用于许多不同场景。几个例子：

- **个人**：追踪自己的目标、健康、心理、自我提升——归档日记条目、文章、播客笔记，逐步构建关于自己的结构化画像。
- **研究**：在数周或数月内深入某个主题——阅读论文、文章、报告，增量构建一个具有演进论点的综合 wiki。
- **读书**：逐章归档，为角色、主题、情节线索及其关联建立页面。读完后你就拥有了一个丰富的伴侣式 wiki。想想 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page) 这样的粉丝 wiki——数千个互相链接的页面覆盖角色、地点、事件、语言，由志愿者社区花数年建成。你可以在阅读过程中由 LLM 完成所有交叉引用和维护工作，个人构建出类似的东西。
- **商业/团队**：由 LLM 维护的内部 wiki，以 Slack 线程、会议记录、项目文档、客户通话为信息源。可能有人工介入审核更新。wiki 保持最新，因为 LLM 承担了团队中没人愿意做的维护工作。
- **竞品分析、尽职调查、旅行规划、课程笔记、爱好深潜**——任何随时间积累知识并希望有序而非散乱的场景。

## 架构

有三层：

**原始来源**——你精心策划的来源文档集合。文章、论文、图片、数据文件。这些是不可变的——LLM 从中读取但绝不修改。这是你的可信来源。

**Wiki**——一个由 LLM 生成的 Markdown 文件目录。摘要、实体页面、概念页面、对比、概述、综合。LLM 完全拥有这一层。它创建页面，在新来源到来时更新它们，维护交叉引用，保持一切一致。你阅读它；LLM 编写它。

**Schema**——一个文档（例如 Claude Code 用 CLAUDE.md，Codex 用 AGENTS.md），告诉 LLM wiki 如何组织、约定是什么，以及摄入来源、回答问题或维护 wiki 时应遵循什么工作流。这是关键的配置文件——它使 LLM 成为一个有纪律的 wiki 维护者，而非通用聊天机器人。你和 LLM 随着对领域的理解而共同演进这个文件。

## 操作

**摄入（Ingest）。** 你将新来源放入原始集合并告诉 LLM 处理它。一个示例流程：LLM 阅读来源、与你讨论关键要点、在 wiki 中撰写摘要页面、更新索引、更新 wiki 中相关的实体和概念页面，并在日志中追加一条记录。一个来源可能涉及 10-15 个 wiki 页面。我个人偏好逐一摄入来源并保持参与——阅读摘要、检查更新、引导 LLM 关注重点。但也可以批量摄入多个来源而减少监督。由你来开发适合自己风格的工作流，并将其记录在 schema 中供后续会话使用。

**查询（Query）。** 你针对 wiki 提问。LLM 搜索相关页面，阅读它们，综合出带引用的答案。答案根据问题可以采取不同形式——Markdown 页面、对比表格、幻灯片（Marp）、图表（matplotlib）、画布。重要的洞察：**好的答案可以作为新页面归档回 wiki。** 你要求的对比、一项分析、你发现的关联——这些都有价值，不应消失在聊天历史中。这样你的探索和摄入的来源一样，在知识库中复利增长。

**检查（Lint）。** 定期让 LLM 对 wiki 做健康检查。查找：页面间的矛盾、被新来源取代的过时论断、没有入站链接的孤立页面、被提及但缺少独立页面的重要概念、缺失的交叉引用、可通过网络搜索填补的数据空白。LLM 擅长建议新问题来研究和新来源来查找。这使 wiki 在增长过程中保持健康。

## 索引和日志

两个特殊文件帮助 LLM（和你）在 wiki 增长时进行导航。它们用途不同：

**index.md** 是面向内容的。它是 wiki 中所有内容的目录——每个页面列出链接、一行摘要，以及可选的元数据如日期或来源数量。按类别组织（实体、概念、来源等）。LLM 在每次摄入时更新它。回答查询时，LLM 先读索引找到相关页面，再深入阅读。这在中等规模（约 100 个来源、约数百个页面）下效果出奇地好，避免了基于嵌入的 RAG 基础设施的需求。

**log.md** 是按时间排序的。它是一个只追加的记录，记录发生了什么以及何时发生——摄入、查询、检查。一个有用的技巧：如果每条记录以一致的格式开头（例如 `## [2026-04-02] ingest | Article Title`），日志就可以用简单的 Unix 工具解析——`grep "^## \[" log.md | tail -5` 给你最近 5 条记录。日志提供了 wiki 演化的时间线，帮助 LLM 了解最近做了什么。

## 可选：CLI 工具

某个阶段你可能想构建小工具帮助 LLM 更高效地操作 wiki。最明显的就是 wiki 页面的搜索引擎——小规模时索引文件就够了，但随着 wiki 增长你需要真正的搜索。[qmd](https://github.com/tobi/qmd) 是一个好选择：它是 Markdown 文件的本地搜索引擎，支持混合 BM25/向量搜索和 LLM 重排序，全部在设备本地运行。它既有 CLI（LLM 可以通过 shell 调用它）也有 MCP 服务器（LLM 可以将其作为原生工具使用）。你也可以自己构建更简单的方案——LLM 可以帮你按需编写一个简单的搜索脚本。

## 技巧与窍门

- **Obsidian Web Clipper** 是一个浏览器扩展，可将网页文章转换为 Markdown。非常适合快速将来源放入原始集合。
- **本地下载图片。** 在 Obsidian 设置 → 文件与链接中，将"附件文件夹路径"设为固定目录（如 `raw/assets/`）。然后在设置 → 快捷键中搜索"Download"找到"下载当前文件的附件"并绑定快捷键（如 Ctrl+Shift+D）。剪藏文章后按快捷键，所有图片就下载到本地磁盘了。这是可选的但很有用——它让 LLM 可以直接查看和引用图片，而不依赖可能失效的 URL。注意 LLM 无法一次性原生阅读含内联图片的 Markdown——变通方法是让 LLM 先读文本，再单独查看部分或全部引用的图片以获取额外上下文。有点笨拙但足够好用。
- **Obsidian 的图谱视图**是查看 wiki 形态的最佳方式——什么连接什么、哪些页面是枢纽、哪些是孤岛。
- **Marp** 是基于 Markdown 的幻灯片格式。Obsidian 有对应插件。适合直接从 wiki 内容生成演示文稿。
- **Dataview** 是一个 Obsidian 插件，可对页面 frontmatter 运行查询。如果你的 LLM 在 wiki 页面中添加 YAML frontmatter（标签、日期、来源数量），Dataview 可以生成动态表格和列表。
- wiki 就是一个 Markdown 文件的 git 仓库。你免费获得版本历史、分支和协作。

## 为什么这能工作

维护知识库的繁琐部分不是阅读或思考——而是簿记。更新交叉引用、保持摘要最新、标注新数据与旧论断的矛盾、维护数十个页面间的一致性。人们放弃 wiki 是因为维护负担的增长速度快于价值增长。LLM 不会厌倦，不会忘记更新交叉引用，可以一次处理 15 个文件。wiki 保持维护是因为维护成本接近零。

人的工作是策划来源、引导分析、提出好问题、思考意义。LLM 的工作是其他一切。

这个思想在精神上与 Vannevar Bush 的 Memex（1945）相关——一个个人的、经过策划的知识存储，文档之间有关联路径。Bush 的愿景更接近这个而非 Web 的现状：私有的、主动策划的，文档之间的连接与文档本身同样有价值。他没能解决的是谁来做维护。LLM 处理了这个问题。

## 说明

本文档有意保持抽象。它描述的是思想，而非具体实现。确切的目录结构、schema 约定、页面格式、工具选择——所有这些都取决于你的领域、偏好和所选的 LLM。上面提到的一切都是可选和模块化的——选有用的，忽略没用的。例如：你的来源可能只有文本，完全不需要图片处理。你的 wiki 可能足够小，索引文件就够用，不需要搜索引擎。你可能不在乎幻灯片，只想要 Markdown 页面。你可能想要完全不同的输出格式集。正确的使用方式是与 LLM Agent 分享本文档，一起实例化适合你需求的版本。本文档的唯一任务是传达这个模式。你的 LLM 可以搞定其余的。
